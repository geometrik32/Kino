# Реестр проблем, доработок и требований (ISSUES)

Документ фиксирует выявленные ошибки, архитектурные ограничения и требования на доработку, чтобы проверять соответствие текущей версии ожиданиям.

Статусы:
- `Открыто` — проблема зафиксирована, исправление не завершено.
- `В работе` — идёт реализация/проверка.
- `Заблокировано` — требуются внешние SDK/инструменты/зависимости для реализации или проверки.
- `Исправлено` — реализовано в коде и проверено.

## ISSUE-001: Нативное воспроизведение сложных кодеков и контейнеров (Desktop + Android)

- **Статус:** `В работе` (часть **Android** + протокол `PlayRequest.native` и UI реализованы в коде; локально пройдены `cargo fmt --all --check`, `cargo check --workspace --all-targets --locked` и `cargo check -p kino-app --target wasm32-unknown-unknown --locked`, ожидает прогона `cargo check/clippy --features mobile`, сборки `.apk` через `.github/workflows/android.yml` и проверки на устройстве; часть **Desktop / Windows** временно отложена по решению владельца)
- **Приоритет:** Высокий (P1)
- **Затронутые платформы:** Windows / macOS / Linux (`kino-app --features desktop` — отложено) и Android (`kino-app --features mobile`), а также серверное API (`kino-core`, `kino-server`).

### Суть проблемы
Сейчас нативные приложения для компьютера (`desktop`) и телефона (`mobile`) используют системный WebView и HTML-элемент `<video>` ([app/src/platform/video.rs](../app/src/platform/video.rs)). Одновременно сервер в `POST /api/play` ([crates/server/src/play.rs](../crates/server/src/play.rs)) жёстко решает совместимость через `probe.browser_ok()` (`mov,mp4` + `h264|vp9|av1` + `aac|mp3|opus|vorbis`), а `PlayInfo::plays_directly()` ([crates/core/src/release.rs](../crates/core/src/release.rs)) отправляет на перекодирование при любом переключении аудиодорожки.

Из-за этого нативные приложения для Windows и Android **не воспроизводят напрямую** `.mkv`, `HEVC`, `HDR`/`Dolby Vision`, `AC3`/`DTS` и не переключают встроенные дорожки без `ffmpeg` на сервере — хотя нативным плеерам это не нужно.

### Что нужно реализовать (для обеих платформ сразу)
1. **Протокол возможностей клиента (`kino-core`, `kino-server`):**
   - Добавить в `PlayRequest` признаки/возможности плеера (например, нативный плеер с поддержкой `mkv`/HEVC/AV1/AC3/DTS и клиентским переключением дорожек), либо явный режим прямого стриминга.
   - Сервер при запросе от нативного клиента должен отдавать `direct = true` и не форсировать `ffmpeg` при смене аудиодорожки, когда плеер сам умеет переключать дорожки внутри потока `GET /api/stream/{token}`.
   - В UI списка раздач (`crates/ui/src/releases.rs`) учитывать тип клиента: не пугать пользователя нативного клиента тегом `перекодируется`, если его плеер воспроизводит этот формат напрямую.
2. **Desktop-плеер (Windows / macOS / Linux):**
   - Встроить нативный движок воспроизведения (рекомендуется `libmpv`) вместо/поверх WebView-слоя, подключив его через абстракцию `app/src/platform/video.rs`.
   - Поддержать аппаратное декодирование, прямое воспроизведение `.mkv`/`mp4`, `HEVC`/`AV1`/`H.264`/`HDR`, переключение встроенных аудиодорожек и субтитров без перезапуска потока и без `ffmpeg`.
   - Сохранить единый UI управления плеером (`PlayerView`), сохранение прогресса каждые 10 секунд, скорость воспроизведения и переход к следующей серии.
3. **Android-плеер (`mobile`):**
   - Подключить нативный движок `ExoPlayer` (`AndroidX Media3`, с поддержкой аппаратных декодеров `HEVC`/`HDR` и при необходимости программного декодирования `AC3`/`DTS`) через JNI/поверхность под WebView, интегрировав его в `app/src/platform/android.rs` и `app/src/platform/video.rs`.
   - Либо предусмотреть промежуточный режим открытия потока, но целевое решение — **встроенный плеер внутри приложения** с сохранением прогресса, переключением дорожек и автопереходом к следующей серии.
4. **Запасной механизм (fallback):**
   - Если на конкретном устройстве нативный декодер всё же не смог открыть файл, сохранять безопасный откат на серверный `ffmpeg`-поток (`force_transcode`).

### Что реализовано (этап Android + общий протокол)
1. **Протокол и сервер ([crates/core/src/release.rs](../crates/core/src/release.rs), [crates/server/src/play.rs](../crates/server/src/play.rs), [crates/server/tests/torrents.rs](../crates/server/tests/torrents.rs)):**
   - В `PlayRequest` и `PlayInfo` добавлен флаг `native: bool` (`PlayInfo::plays_directly` всегда `true` при `native`);
   - В `POST /api/play` при `req.native == true` отдаётся `direct = true` и сохраняется `subtitle_track` даже для потоковых торрент-раздач без предзагрузки; добавлена проверка `native: true` в интеграционный тест `transcodes_with_ffmpeg`.
2. **UI списка раздач и слот плеера ([crates/ui/src/releases.rs](../crates/ui/src/releases.rs), [crates/ui/src/player.rs](../crates/ui/src/player.rs), [crates/ui/src/style.css](../crates/ui/src/style.css), [crates/preview/src/main.rs](../crates/preview/src/main.rs), [app/src/main.rs](../app/src/main.rs)):**
   - В `ReleasePicker` передаётся `native_player = cfg!(feature = "mobile")` и сбрасывается дефолтный фильтр `direct_play`: скрываются фильтры «Играет сразу» / «Без перекодирования» и бейдж «перекодируется»;
   - В `PlayerState` / `PlayerView` добавлен `native_video: bool`: вместо `<video>` рендерится прозрачный слот `<div id="kino-video" class="p-native-slot">`, меню субтитров доступно без предзагрузки, а при `html.native-video` фон и элементы страницы позади `.player.native-video` скрываются, чтобы просвечивал нативный видеослой.
3. **Android ExoPlayer + Jellyfin FFmpeg и CI ([app/Dioxus.toml](../app/Dioxus.toml), [app/android/MainActivity.kt](../app/android/MainActivity.kt), [app/android/proguard-kino.pro](../app/android/proguard-kino.pro), [app/src/platform/android.rs](../app/src/platform/android.rs), [app/src/platform/video.rs](../app/src/platform/video.rs), [app/src/player.rs](../app/src/player.rs), [.github/workflows/android.yml](../.github/workflows/android.yml)):**
   - Подключены `androidx.media3:media3-exoplayer:1.9.0`, `androidx.media3:media3-ui:1.9.0`, `org.jellyfin.media3:media3-ffmpeg-decoder:1.9.0+1`, `compile_sdk`/`target_sdk = 35`, `uses_cleartext_traffic = true`, `large_heap = true`, ProGuard-правила для JNI и Media3;
   - В `MainActivity.kt` поверх `WryActivity` за `WebView` размещён контейнер с `AspectRatioFrameLayout`, `TextureView` и `SubtitleView`, реализованы `ExoPlayer` (`EXTENSION_RENDERER_MODE_ON`), выбор дорожек, `keepScreenOn` на время воспроизведения, защита от гонок `openSeq`/`seekSeq` и экспорт снимка состояния через JNI;
   - В `video.rs` и `player.rs` нативный `ExoPlayer` подключён ко всем существующим сценариям плеера (перемотка, пауза/воспроизведение, скорость, громкость, живое переключение аудио и субтитров без перезапуска потока, прогресс каждые 10 с, следующая серия, синхронизация устройств, `NativePlayerGuard` при размонтировании и откат на серверное перекодирование в `force_transcode` при ошибке декодера);
   - Создан workflow `.github/workflows/android.yml` для сборки и публикации `orel-kino-arm64.apk`.

### Критерии приёмки
- [ ] На Android релиз с `HEVC` + `.mkv` + `AC3`/`DTS` + несколькими аудиодорожками и субтитрами запускается напрямую через `GET /api/stream/{token}` без запуска `ffmpeg` на сервере; переключение дорожек, перемотка, сохранение прогресса и переход к следующей серии работают на реальном устройстве.
- [ ] Пройдены CI-проверки `cargo clippy -p kino-app --no-default-features --features mobile --target aarch64-linux-android` и сборка `.apk` в `.github/workflows/android.yml`, а также полный workspace CI `.github/workflows/ci.yml` (включая серверный тест `transcodes_with_ffmpeg`).
- [ ] Веб-версия и Telegram Mini App продолжают автоматически использовать `ffmpeg`-транскодирование для несовместимых форматов.
- [x] UI скрывает тег «перекодируется» и фильтры перекодирования для нативного Android-клиента (проверено в коде/check, ждёт живой проверки на устройстве).
- [ ] (Отложено) На Windows/Desktop реализовано и проверено нативное воспроизведение без серверного `ffmpeg`.

## ISSUE-002: Ограничения локального сборочного окружения на текущей Windows-машине

- **Статус:** `Открыто`
- **Приоритет:** Средний (P2, инфраструктура разработки)
- **Затронутые платформы:** Локальная сборка и проверка на текущей машине под Windows.

### Наблюдаемые проблемы
1. На текущей Windows-машине отсутствуют C-компилятор и линкер в `PATH`:
   - для `stable-x86_64-pc-windows-gnu` не найдены `gcc.exe` и `dlltool.exe` (ошибка сборки `ring`, `libloading`, `parking_lot_core`, `windows-sys`);
   - для `stable-x86_64-pc-windows-msvc` не найден `link.exe` (Visual Studio C++ Build Tools).
2. При сборке в папке по умолчанию (`Kino/target`) компоновщик MinGW `ld` падает на пути с кириллицей (`Свой стриминговый сервис`), требуется `CARGO_TARGET_DIR` без кириллицы (например, `F:\tmp\kino-target`).
3. Не установлены инструменты сборки мобильного/десктопного клиента и нативного плеера:
   - отсутствует `dx` (`dioxus-cli` 0.7);
   - не заданы `ANDROID_HOME` и `ANDROID_NDK_HOME`, не установлен target `aarch64-linux-android`;
   - не установлены `libmpv` / `mpv`.

### Критерии приёмки
- [ ] Установлен рабочий C-тулчейн (Visual Studio Build Tools для `msvc` или MinGW-w64 для `gnu`) и настроен путь сборки без кириллицы (или `msvc` линкер).
- [ ] Успешно проходят `cargo check --workspace` и `cargo test --workspace`.
- [ ] Для сборки приложений установлены `dx`, Android SDK 34 + NDK 27 и зависимости нативного плеера.

## ISSUE-007: Улучшение Telegram-бота — кнопки команд, поиск с `е`/`ё` и карточки фильмов с постером и описанием

- **Статус:** `Исправлено` (локальные unit-тесты `kino-bot` и `kino-server --lib` пройдены; `clippy`/`rustfmt` и полный CI-прогон с БД остаются на GitHub Actions)
- **Приоритет:** Высокий (P1)
- **Затронутые платформы:** Telegram-бот (`kino-bot`) и общий слой каталога (`kino-server/src/catalog`).

### Суть проблемы
1. **Нет наглядных кнопок команд в Telegram-боте:** после `/start` показывается только кнопка «Открыть кинопоказ», а системная кнопка меню заменена на кнопку Mini App («Кино»). Пользователю неочевидно, какие команды поддерживает бот (`/search`, `/continue`, `/my`, `/login`, `/help`, `/invite`).
2. **Поиск не находит фильмы при замене `ё` на `е`:** например, запрос «Зеленая линия» (через `е`) не находит «Зелёная линия» в TMDB и в демо-каталоге («темный» не находит «Тёмный рыцарь»).
3. **Скудная выдача фильмов в поиске:** бот отправляет простой текстовый список названий без постеров и описаний.

### Что реализовано
1. **Кнопки команд в боте (`crates/bot/src/screens.rs`, `crates/bot/src/main.rs`):**
   - В личном чате `/start` (и подсказка `/search`) отправляет постоянную клавиатуру (`ReplyKeyboardMarkup`: `🎲 Случайный фильм`, `🔍 Поиск`, `▶ Продолжить`, `📚 Мои списки`, `🌐 Вход на сайт`, `❓ Помощь`, и для админов `🎟 Пригласить`) без дублирования кнопки «Открыть кинопоказ», которая уже закреплена слева от поля ввода (`MenuButton::WebApp` «Кино»); при заходе по приглашению `inv_<code>` дополнительно выдаётся кнопка открытия по приглашению, а в `/help` и неличных чатах выводятся inline-кнопки команд (`cmd:<action>`).
   - Нажатия кнопок клавиатуры и inline-кнопок маршрутизируются на те же обработчики действий (`run_action`).
2. **Поиск с поддержкой `е`/`ё` (`crates/server/src/catalog/mod.rs`, `demo.rs`, `tmdb.rs`):**
   - Добавлена нормализация (`normalize_search_text`, `matches_normalized_query`): приведение регистра, замена `ё → е`, схлопывание пунктуации.
   - `DemoCatalog::search` использует нормализованное сопоставление.
   - `TmdbCatalog::search` при отсутствии нормализованного совпадения в первичном ответе параллельно запрашивает варианты с заменой `ё ↔ е` (`yo_query_variants`) и при необходимости ищет по якорному слову без `е`/`ё` (`anchor_word_query`), объединяет результаты без дубликатов и поднимает нормализованные совпадения вверх.
3. **Карточки фильмов с постером и описанием (`crates/bot/src/screens.rs`, `crates/bot/src/main.rs`):**
   - Для первых `SEARCH_CARD_LIMIT = 3` результатов поиска бот загружает постеры через `Catalog::image` (с таймаутом и fallback на текстовую карточку при отсутствии постера) и отправляет карточки (`send_photo`) с названием, оригинальным названием, годом, типом, рейтингом, описанием (`overview`, с безопасным усечением в лимит подписи Telegram) и кнопкой открытия в кинопоказе.
   - Остальные результаты (до `LIST_LIMIT = 8`) выводятся кнопками (`card:<kind>:<id>`), по нажатию на которые загружается детальная карточка (`title_details_card` с жанрами и длительностью) и постер.

### Критерии приёмки
- [x] В коде бота добавлены кнопки всех доступных команд (`ReplyKeyboardMarkup` и inline-кнопки в `/help`) и их обработчики.
- [x] В коде каталога реализована нормализация и резервный поиск с `е`/`ё` (добавлены unit-тесты в `catalog/mod.rs`, `demo.rs`, `tmdb.rs`).
- [x] В коде бота реализована выдача карточек фильмов с постером, описанием и кнопкой открытия (добавлены unit-тесты в `screens.rs`).
- [x] Пройдены сборка и unit-тесты (`cargo build -p kino-bot --locked`, `cargo test -p kino-bot --locked` — 18 passed, `cargo test -p kino-server --lib --locked` — 54 passed).
- [ ] Пройдены `cargo fmt --all --check`, `cargo clippy` и интеграционные тесты в CI (локально не установлены `cargo-fmt` и `cargo-clippy`).

## ISSUE-008: Подбор случайного фильма по параметрам и полировка UX Telegram-бота

- **Приоритет:** Высокий (P1)
- **Затронутые платформы:** Telegram-бот (`kino-bot`) и слой каталога (`kino-server/src/catalog`).

### Суть задачи
1. Добавить в Telegram-бот рекомендацию одного случайного фильма (команда `/random` и кнопка `🎲 Случайный фильм`):

## ISSUE-004: Бесконечное зависание плеера на «Ищем раздающих…»

- **Статус:** `Исправлено` (ожидает сборки/проверки в CI и деплоя)
- **Приоритет:** Критический (P0)
- **Затронутые платформы:** Сервер (`kino-server`) и клиент (`kino-app` / `kino-ui`).

### Суть проблемы
1. **Взаимная блокировка `TorrServer` (`MatriX.141.5`) при повторном добавлении активного торрента и сохранение в БД при `save="false"`:**
   - В `POST /torrent/upload` передавалось `.text("save", "false")`, но TorrServer трактует любое непустое значение `save` как `true` и сохранял торренты в `config.db`.
   - Повторный вызов `/torrent/upload` или `/torrents {"action":"add"}` для уже активного в памяти торрента приводил к deadlock внутри TorrServer: запросы `add`/`list` зависали навсегда, а у `TorrServer::add` в [torrserver.rs](../crates/server/src/torrent/torrserver.rs) не было HTTP-таймаута, из-за чего `POST /api/play` висел минутами до обрыва клиентом (`499`), пока `GET /api/play/progress/{release}` отвечал `Connecting` с `peers: 0` («Ищем раздающих…»).
2. **Небезопасный разбор `null` от TorrServer:** `#[serde(default)]` для `file_stats` и других полей в `Status`/`Stats` падал на явном JSON `null` (Go `nil` slice), а `play_progress` молча возвращал `StreamProgress::default()` через `.unwrap_or_default()`.
3. **Заглушение таймаута `ffprobe` и потоки без таймаута в [play.rs](../crates/server/src/play.rs) / [ffmpeg.rs](../crates/server/src/torrent/ffmpeg.rs):**
   - При провале/таймауте `ffprobe` сервер подставлял `Probe::default()` и отдавал `200 OK`, после чего транскодированный поток в `stream()` сразу отправлял `200 OK` с телом из `ffmpeg` без таймаута (и `proxy()` ждал TorrServer без таймаута).
4. **Отсутствие таймаутов в клиенте ([app/src/player.rs](../app/src/player.rs), [crates/ui/src/player.rs](../crates/ui/src/player.rs)):** цикл опроса не завершал зависший старт воспроизведения по таймауту и продолжал опрашивать TorrServer даже для `preloaded`-релизов.

### Что исправлено
- [torrserver.rs](../crates/server/src/torrent/torrserver.rs): перед добавлением проверяется `POST /torrents {"action":"get"}` (если торрент уже активен `stat 1..=3` и есть `file_stats`, повторная загрузка не делается); убрано `.text("save", "false")` в `/torrent/upload`; добавлены `null_as_default` и HTTP-таймауты на `upload`/`add`/`get`.
- [ffmpeg.rs](../crates/server/src/torrent/ffmpeg.rs): для HTTP(S)-источников добавлен `-rw_timeout 30000000` в `probe` и `transcode_args`, таймаут `probe` сокращён до 45 с.
- [play.rs](../crates/server/src/play.rs): при провале `ffprobe` на не-`preloaded` релизе проверяется `ts.progress` (при `peers == 0 && loaded_bytes == 0 && speed_bps == 0` возвращается `503`); ошибки `ts.progress` логируются; `stream()` ждёт первый чанк от `ffmpeg` до 45 с перед отправкой `200 OK`; `proxy()` ограничивает ожидание заголовков от TorrServer 45 с.
- [app/src/player.rs](../app/src/player.rs) и [crates/ui/src/player.rs](../crates/ui/src/player.rs): добавлены генерация попыток `play_gen`, клиентские таймауты ожидания (`95s` на `api::play`, `45–60s` при нулевом прогрессе после старта), пропуск опроса прогресса для `preloaded` и скрытие спиннера при наличии `s.error`.

## ISSUE-009: Голый спиннер без подложки, блокировка `<video>` субтитрами, `503` на слотах и строгий фильтр по языку озвучки

Обновлены тесты в `play.rs` и `crates/server/tests/torrents.rs`.

## ISSUE-012: Видимость системного интерфейса Android, автопауза при запуске из бота/синхронизации и смещение иконки Play

## ISSUE-017: Масштабирование картинки в плеере («По ширине» и «По высоте» с запоминанием для фильма)

- **Статус:** `Исправлено` (реализовано в коде с сохранением в PostgreSQL + локальным кешем; результаты финального `cargo check` ниже)
- **Приоритет:** Средний (P2)
- **Затронутые платформы:** Сервер и БД (`kino-core`, `kino-server`, миграция `0008_video_scale.sql`), все клиенты (`kino-ui`, `kino-app` для Web, Telegram Mini App, Desktop и Android `ExoPlayer`), превью (`kino-preview`).

### Суть требования
Добавить в видеоплеер возможность переключать масштабирование картинки между ровно 2 пропорциональными режимами:
1. **«По ширине» (`VideoScale::FitWidth`)** — ширина видео подтягивается к ширине экрана, высота масштабируется пропорционально (при несовпадении пропорций даёт полосы сверху/снизу либо аккуратно обрезает верх/низ).
2. **«По высоте» (`VideoScale::FitHeight`)** — высота видео подтягивается к высоте экрана, ширина масштабируется пропорционально (при несовпадении пропорций даёт полосы по бокам либо аккуратно обрезает края слева/справа).

До ручного выбора пользователем для конкретного фильма/сериала стартовый режим автоматически подбирается без обрезки кадра (в тот из двух режимов, который вписывает кадр целиком для текущего соотношения сторон экрана и видео), а переключение кнопкой сохраняет выбор в БД (`title_state.video_scale`) для этого тайтла (`(kind, tmdb_id)`) на всех устройствах (с локальным fallback/кешем в `localStorage`).

### Суть требования
При выставлении пользовательской оценки тайтлу (`PUT /api/title/{kind}/{tmdb_id}/rating`, 1–5 звёзд):
1. Статус тайтла должен автоматически становиться `Просмотрено` (`TitleStatus::Watched`), даже если до этого он был не задан или имел другой статус (`Хочу посмотреть`, `Смотрю`, `Брошено`).

4. При снятии оценки (`rating = null`) уже выставленные статус и прогресс просмотра не должны сбрасываться.
5. В интерфейсе карточки тайтла (`app/src/main.rs`, `crates/ui/src/lib.rs`) после выставления оценки должны сразу обновляться статус, прогресс по сериям/сезонам и кнопка «Смотреть».

## ISSUE-019: Ошибки воспроизведения «Сверхъестественного» — падение VA-API на `.avi` (`mpeg4`), `_` в `files::episode_of` и OOM TorrServer на больших паках

- **Статус:** `Исправлено` (исправлено в рамках `ISSUE-022` и `ISSUE-023`: добавлен гибридный фильтр VA-API с программным декодом и логирование `stderr` `ffmpeg`, исправлены регулярки `files::episode_of` для разделителя `_`, а буфер `torrserver` переведён на HDD с `GOMEMLIMIT`; ожидает прогона CI и выкатки на сервер)
- **Приоритет:** Критический (P0)
- **Затронутые платформы:** Сервер (`kino-server`: `torrent/ffmpeg.rs`, `torrent/files.rs`, `play.rs`, `torrent/token.rs`) и деплой (`deploy/compose.yaml`).

### Суть проблем
По логам `kino-server`, `traefik`, `torrserver` и проверке потоков внутри контейнеров для сериала «Сверхъестественное» (`tv/1622`) выявлены три независимые проблемы:

1. **Крах `ffmpeg` с `TRANSCODE_HWACCEL=vaapi` на `mpeg4` (`.avi` / `XVID`):**
   - В раздаче `Supernatural.2005-2020.hdrip_[teko]` (`ec60cd427cf13a411c662aaa9495788cc2eb9cdd`, `Season_01/s01e01_Pilot.avi`) видео имеет кодек `mpeg4` (`XVID`) + аудио `ac3`.
   - В [crates/server/src/torrent/ffmpeg.rs](../crates/server/src/torrent/ffmpeg.rs) при `HwAccel::Vaapi` и `!copy_video` всегда передаются `-hwaccel vaapi -hwaccel_device /dev/dri/renderD128 -hwaccel_output_format vaapi` и фильтр `-vf scale_vaapi=format=nv12 -c:v h264_vaapi`.
   - Аппаратный декодер Intel (`i3-10100`, `iHD_drv_video.so`) не поддерживает декодирование `mpeg4`: `ffmpeg` падает с кодом `218` (`No support for codec mpeg4 profile 15` / `Function not implemented` в `scale_vaapi`) за ~640 мс без единого байта на stdout, `stream()` отдаёт `503 Service Unavailable`, а клиент показывает ошибку «Видеопоток не запустился или был прерван...».
   - При программном декодировании с загрузкой на VA-API (`-vaapi_device /dev/dri/renderD128 ... -vf format=nv12,hwupload -c:v h264_vaapi`) тот же файл кодируется без ошибок (`exit=0`).
   - Также `ffmpeg::spawn` скрывает `stderr` (`Stdio::null()`), из-за чего в логах `kino-server` нет причины падения `ffmpeg`.

2. **Регулярки `files::episode_of` в [crates/server/src/torrent/files.rs](../crates/server/src/torrent/files.rs) не распознают серии с подчёркиванием `_` (`s01e01_Pilot.avi`):**
   - В `SE` (`\bs(\d{1,2})[ ._-]?e(\d{1,3})\b`) и `EP` / `SEASON_DIR` используется `\b`, для которого `_` считается символом слова (`\w`).
   - На всех 327 файлах раздачи `ec60cd...` (`Season_01/s01e01_Pilot.avi` и т.д.) `episode_of` возвращает `(Some(season), None)`. Для `S01E01` нужный файл выбран случайно (он первый в отсортированном списке), но для любого другого сезона (`S02E01`, `S03E01` и т.д.) `files::pick` игнорирует сезон и тоже выбирает файл из 1-го сезона (или возвращает `404`, если в раздаче попадётся хотя бы один файл без `_`).

3. **OOM-kill `orel-kino-torrserver-1` при лимите `512m` на 327/328-файловых паках:**
   - В [deploy/compose.yaml](../deploy/compose.yaml) контейнеру `torrserver` задан `mem_limit: 512m`.
   - Даже одна активная 328-файловая раздача (`0e3c84...`, `Supernatural [S1-15] BDRip-HEVC 1080p`) доводит RSS TorrServer до `~446 MiB / 512 MiB` (`87%`); при переключении между раздачами в `17:52:52` UTC процесс превысил лимит (`anon-rss: 518816 kB`) и был убит ядром (`oom-kill`). Кроме того, при старте с низкой скоростью сидов у `0e3c84...` `ffprobe` упирался в 45-секундный таймаут, а перемотка `-ss 117` по большому HEVC MKV через TorrServer занимала ~40–87 с.

### Критерии приёмки
- [ ] Транскодирование с `TRANSCODE_HWACCEL=vaapi` (и `qsv`) успешно запускает видео с кодеками, не поддерживаемыми аппаратным декодером (включая `mpeg4` / `XVID` в `.avi`), через программный декодер + `hwupload` (или программное перекодирование), а ошибки раннего завершения `ffmpeg` логируются сервером.
- [ ] `files::episode_of` и `files::pick` корректно определяют сезон и серию при разделителе `_` (включая `Season_01/s01e01_Pilot.avi`, `Season_02/s02e01_...`, `Show_S02E05_720p.mkv`), подтверждено unit-тестами.

   - В строках вкладки «Настройки → Качество» (плюс в резервной строке текущей раздачи до загрузки списка) добавлена кнопка скачивания на сервер, актуальный прогресс в `%` при открытии меню, бейдж `На сервере` и кнопка ручного переключения `С диска`, если локальный файл уже готов.
3. **Серверное уведомление о завершении загрузки и плашка перехода (`crates/core/src/sync.rs`, `crates/server/src/userdata.rs`, `jobs.rs`, `sync.rs`, `crates/ui/src/player.rs`, `app/src/player.rs`):**
   - `jobs::sync_preloads` теперь опрашивает активные закачки каждые 5 с и по атомарному переходу `queued/downloading -> ready` в `preload_progress` рассылает активным плеерам пользователя по WebSocket сообщение `SyncServerMsg::PreloadReady`.
   - При получении `PreloadReady` для текущей онлайн-раздачи поверх видео без затемнения, приглушения звука и автопаузы появляется плашка в формате «Следующей серии» («Фильм/Сезон скачался — Хотите сразу его воспроизвести?») с кнопками «Да» (перезапускает поток с локального диска с отмоткой на 1 с назад) и «×» (отменяет плашку без вмешательства в просмотр).
